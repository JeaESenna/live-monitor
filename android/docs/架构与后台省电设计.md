# 架构与后台省电设计

> 状态：**v1.1.0 文档更新（2026-11-13）**。本文描述 Android 版的实际架构与省电策略；动态验证数据来自 Lead 在 LDPlayer 的实测（v1.0.0 已完成，v1.1.0 待补），**未经真机验证**的量级估计均已明确标注。
> 安全设计逐项见 `威胁模型.md`，平台访问合规见 `合规评估.md`，实测结论见 `安全测试报告.md`。

## 1. 总体架构

```
┌─────────────────────────────── App 进程（com.livemonitor.app） ───────────────────────────────┐
│                                                                                              │
│  MainActivity (Compose, 唯一导出组件)                                                         │
│     └─ MainViewModel ──► AppRepository (StateFlow，唯一数据源)                                │
│            │                   │  └─ KvStore → SharedPreferences(MODE_PRIVATE)                │
│            │                   │                                                              │
│            └─ MonitorControl ──┼─ 显式 Intent（ACTION_START/STOP/PAUSE/WAKE/DISMISS/MUTE）──┐ │
│                                ▼                                                             │ │
│  MonitorService（前台服务，exported=false, foregroundServiceType=specialUse）                │ │
│     ├─ 单协程 engineLoop（Dispatchers.IO，顺序轮询）                                          │ │
│     │    ├─ MonitorEngine（状态机：可靠立即提交 / 不可靠连续2次 / 3分钟提醒冷却）              │ │
│     │    ├─ PlatformApi.check ─► PlatformCheckers ─► HttpFetcher(OkHttp) ─► 5 平台公开页面/接口│ │
│     │    │        └─ PlatformParsers（纯函数、防御性解析）+ PlatformText 清洗                  │ │
│     │    ├─ persistOutcome → AppRepository（写回列表状态）+ requestSave（异步落盘）           │ │
│     │    └─ maybeNotify → AlertPolicy.shouldAlert → AlertNotifier                           │ │
│     ├─ AlertNotifier（主线程 Handler + 锁；最多 4 条通知、自动关闭、循环音调度）               │ │
│     │    ├─ NotificationHelper（两个渠道 + 通知构造 + PendingIntent）                         │ │
│     │    └─ LoopSoundPlayer（MediaPlayer + 瞬时音频焦点）                                     │ │
│     ├─ 短暂 PARTIAL_WAKE_LOCK（单房间检测，10s 超时）                                         │ │
│     └─ 常驻低优先级通知（前台服务要求，含暂停/停止动作）                                       │ │
│                                                                                              │
│  AppLog（应用私有 files/logs，1MB 轮转 + 上一份，URL/凭据脱敏）                                 │
└──────────────────────────────────────────────────────────────────────────────────────────────┘
外部：斗鱼 / 虎牙 / B站 / 抖音 / 快手 的公开页面与公开接口（仅 HTTPS，域名精确白名单）
```

### 1.1 组件职责

| 组件 | 职责 | 安全/省电要点 |
| --- | --- | --- |
| `App` / `AppGraph` | 进程初始化、单例仓储 | 无 DI 框架；`AppLog.init` 先于日志使用 |
| `AppRepository` + `KvStore` | 房间/设置单一数据源；串行异步落盘 + 同步 flush；损坏恢复 | `MODE_PRIVATE`；读取时全量防御性校验；URL 重新规范化 |
| `MonitorService` | 前台服务生命周期、轮询循环、命令处理 | `specialUse` + property；`START_STICKY`；启动失败安全退出；`stopWithTask=false` |
| `MonitorEngine` | 状态机（与桌面版 `RoomMonitor.Raise` 等价） | 不可靠结果连续 2 次才覆盖；同一房间 180s 提醒冷却 |
| `AlertPolicy` / `AlertCenter` | 纯逻辑：文案、通知 ID、上限、mute、退避倍率 | 文案清洗限长；通知 ID 防碰撞；最多 4 条 |
| `AlertNotifier` | 通知生命周期、自动关闭、循环音调度 | 全部 `FLAG_IMMUTABLE` 显式 PendingIntent；锁屏 PRIVATE |
| `NotificationHelper` | 渠道与通知构造 | 常驻通知静音低优先级；提醒通知 HIGH + 内置 chime + 振动 |
| `LoopSoundPlayer` | 循环提示音 | 遵循通知开关/免打扰/静音/通知音量；瞬时 duck 音频焦点；单播放器 |
| `PlatformApi` / `UrlPolicy` | 输入解析、URL 白名单、检测入口 | 只产出规范 https URL；持久化 URL 精确域名校验 |
| `TlsPolicy` / `PlatformHttp` | TLS 证书固定与运行期切换 | CA 家族级 SPKI pin（GlobalSign/DigiCert，默认开启）；TLS1.2+；开关变化时换用对应 OkHttpClient |
| `JumpTargets` / `RoomLauncher` / `RoomJumpActivity` | 进入直播间：目标构造、外部启动、选择弹窗 | URL 仅来自已校验房间数据/固定常量；平台 App `setPackage`；Activity 未导出只收本地 key；统一 NEW_TASK+异常兜底 |
| `CustomSoundStore` / `CustomSoundPolicy` / `AlertSoundPlayer` | 自定义提示音导入、校验、播放 | SAF 导入无存储权限；2MB/格式/解码校验；固定文件名内部目录；损坏回退内置音 |
| `AlertNotifier` / `NotificationHelper` | 提醒通知/循环音/渠道 | `live_alerts_v2` 静音渠道 + App 播放器首声；删除旧渠道；PendingIntent 全部 IMMUTABLE |
| `PlatformCheckers` / `PlatformParsers` / `Sanitizers` | 平台网络编排与防御性解析 | 主路径优先、失败降级；正则带上界；所有展示字段清洗 |
| `HttpFetcher` | OkHttp 抓取 | 手动重定向逐跳校验；3MB 响应上限；15s 整体超时；内存 Cookie；**TLS1.2+ + CA 家族级证书固定（默认开启，见 `TlsPolicy`）** |
| `MainActivity` / `MainScreen` / `SettingsScreen` | Compose UI | 唯一导出组件；无深链接/无外链跳转；通知权限一次性引导 |

## 2. 线程与并发模型

- **单一监测协程**：`MonitorService.serviceScope = SupervisorJob + Dispatchers.IO`，`engineLoop` 内串行处理所有房间。不存在并行请求同一平台的情况。
- **UI 与服务共享状态**：通过 `AppRepository.state`（`StateFlow`）单向数据流；写操作在 `synchronized(stateLock)` 内完成，持久化由 `Channel(CONFLATED)` + IO 串行执行，避免并发写坏配置。
- **提醒调度**：`AlertNotifier` 使用主线程 `Handler` 做自动关闭/循环音定时；共享状态用 `synchronized(lock)` 保护。
- **唤醒通道**：`Channel<Unit>(CONFLATED)` 承载“立即检测/设置变更”，连续多次唤醒会合并为一次，不会积压成串行重试。
- **异常隔离**：单轮/单房间/单条解析的异常都被捕获并记录，循环不退出；`MonitorEngine` 的不可靠结果需连续 2 次才覆盖已知状态，避免网络抖动误报。

## 3. 轮询策略

| 参数 | 值 | 说明 |
| --- | --- | --- |
| 检测间隔 | 15–3600s，默认 **60s** | 桌面版默认 30s；移动端考虑省电与平台风控默认 60s。设置变化后立即唤醒重排。 |
| 房间顺序间隔 | 120ms + 0–2000ms 随机抖动 | 与桌面版单线程 120ms 等效，并打散固定节奏，降低被识别为脚本轮询的概率。 |
| 单次请求超时 | 连接 5s / 读 10s / 整体 15s | OkHttp `callTimeout`；单房间失败快速返回等下一轮。 |
| 响应体上限 | 3MB | 超限按解析失败处理，不继续下载。 |
| 重定向上限 | 5 跳，逐跳白名单校验 | 防 SSRF/开放重定向劫持。 |
| 连续失败退避 | ×1 / ×2 / ×4（上限），失败计数封顶 8 | 只有 TIMEOUT/NETWORK/HTTP_STATUS/UNKNOWN 计入；PARSE/POLICY 不计入（避免退避掩盖配置错误）。 |
| 无网络 | 跳过本轮、零请求 | 仅更新运行状态并累计失败计数。 |
| 空房间列表 | 2s 轻量等待 | 零网络、零 CPU，等待期间可被设置变更唤醒。 |
| 成功恢复 | 下一轮立即恢复基础间隔 | 网络恢复后不残留长退避。 |

## 4. 前台服务（specialUse）设计

### 4.1 v1.1.0 新增：后台自动打开与通知“进入直播间”

- **进入直播间（用户主动，v1.1.1 收敛）**：列表/通知动作 → `RoomJumpActivity`（未导出，只收本地 room key）→ `RoomLauncher`：平台 App（`setPackage`）→ 未安装/失败则弹窗**仅提供“用浏览器打开网页版/取消”**并提示自行在应用商店下载安装（**不再有下载 App/应用市场/官网链接**）。全程 NEW_TASK + 异常兜底；无 `QUERY_ALL_PACKAGES`（queries 5 包 + https 浏览器解析）。
- **自动打开（默认关闭）**：`MonitorService` 在提醒成功发出后启动独立协程，3 秒后经 `RoomLauncher.autoOpen` 尝试一次；`autoOpenPending` 去重（同一时间只排队一个），执行前重读设置。**限制**：Android 10+ 后台 Activity 启动（BAL）可能被系统静默拦截，且无法可靠检测 → 只记录结果、不重试、不影响监测与通知（SEC-103）。
- **通知渠道迁移**：`live_alerts` → `live_alerts_v2`（静音渠道；首声改由 `AlertSoundPlayer` 播放，遵循系统静音/勿扰/通知音量/渠道开关），升级时删除旧渠道（旧渠道自定义声音设置丢失，SEC-104）。
- **自定义提示音**：SAF 导入 → `CustomSoundStore` 复制到 `filesDir/sounds/custom_alert.<ext>`（2MB 上限、固定文件名、MediaPlayer 解码校验）→ 首声/循环音/试听共用 `AlertSoundPlayer`，只从内部固定目录读取，损坏/不支持时回退内置 `chime.wav`。

- **Manifest**：`android:exported="false"`、`android:foregroundServiceType="specialUse"`、`stopWithTask="false"`、`PROPERTY_SPECIAL_USE_FGS_SUBTYPE` 说明用途（本地开播提醒，不收集远程数据）。
- **权限**：`FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_SPECIAL_USE`；Android 14+ 启动时通过 `ServiceCompat.startForeground(..., FOREGROUND_SERVICE_TYPE_SPECIAL_USE)` 显式声明类型。
- **常驻通知**：`IMPORTANCE_LOW`、静音、无角标、`setOngoing(true)`，文案含“房间数/直播中数/最后检测时间”，带「暂停/继续」「停止」动作（显式 PendingIntent，`FLAG_IMMUTABLE`）。
- **启动/停止路径**：
  - `ACTION_START` 由 UI 调 `startForegroundService`；服务在 5 秒内 `startForeground`。
  - 其它动作（暂停、唤醒、忽略、不再提醒）用 `startService` 显式 Intent；若服务已不在前台，服务只做尽力清理后安全退出，**绝不**因“未及时 startForeground”崩溃。
  - `startForeground` 失败（如 Android 12+ 后台启动限制、通知权限异常、个别 ROM）→ 记录日志并 `stopSelf()`，不崩溃。
- **START_STICKY**：进程被系统回收后系统重建服务（null Intent）；若用户已关闭监测（`monitorEnabled=false`）则优雅退出，不会“偷偷”恢复。
- **Android 15（API 35）说明**：`specialUse` 不在“6 小时/24 小时”时限的类型（该限制针对 `dataSync`/`mediaProcessing`），但 Play 商店要求如实申报用途；不可将其用于用户不知情的后台活动。
- **用户划掉最近任务**：`stopWithTask=false`，监测继续（用户只是收起界面）；常驻通知始终可见、可随时停止。

## 5. 唤醒锁（WakeLock）策略

- 类型：`PowerManager.PARTIAL_WAKE_LOCK`（仅保持 CPU，不亮屏），tag `LiveMonitor:check`，`setReferenceCounted(false)`。
- 持有范围：**仅单个房间检测期间**；进入 `checkOne` 时 `acquire(10_000ms)`，`finally` 中立即 `release()`；超时自动释放兜底。
- 不跨房间、不跨轮持有；等待下一轮时零唤醒锁、零 CPU。
- 与桌面版的差异：桌面版用事件等待（`AutoResetEvent`）不持锁；移动端需要覆盖亮屏/息屏切换时的一轮紧凑网络请求，因此采用“短持锁”。
- 深睡（Doze）时：即便持锁也只保证 CPU 可用，**网络仍受 Doze 约束**（见第 7 节），提醒可能延迟到维护窗口。

## 6. 内存 / CPU 预期（含阶段三模拟器实测）

> 阶段三由 Lead 在 **LDPlayer 14（Android 14/API34/x86_64/1600x900）** 安装签名 release APK 实测：**PSS ≈ 41 MB、idle CPU ≈ 0%**（UI+服务同进程，v1.0.0 读数）。这是**模拟器环境读数**，v1.1.0 **未复测** PSS/CPU，真机 ARM/厂商 ROM 可能有差异，发布前建议用 `dumpsys meminfo` / `batterystats` 在目标机型复核。下表“预期”列为设计目标，不是多机型实测承诺。

| 指标 | 预期 | 依据 |
| --- | --- | --- |
| 空闲 CPU | ≈0%（等待期间只有协程挂起；LDPlayer 模拟器观察一致） | 单线程 `delay`/`withTimeoutOrNull`；无常驻定时器轮询 |
| 轮询时 CPU | 单房间一次网络+解析，毫秒~百毫秒级 | 单线程顺序；解析为正则/JSON |
| 常驻内存（PSS） | LDPlayer 模拟器实测 ≈41MB（UI+服务同进程）；真机预计 40–150MB 区间 | 模拟器读数由 Lead 提供；真机需复核 |
| 流量 | 每房间每轮 1~3 个 HTTPS 请求（按平台降级路径） | 页面/接口体积多在几十 KB 内；3MB 上限兜底 |
| 电量 | 默认 60s×10 房间 ≈ 每小时约 600 请求；开销主要在 radio 待机 | 建议用户按需调大间隔；无网络/空列表时几乎零开销 |

**降低开销的建议**：减少监测房间数、调大检测间隔（默认 60s 已是省电取舍）、关闭循环提示音、勿将 App 加入电池优化白名单（除非确需及时提醒）。

## 7. Doze 与厂商杀后台的局限（如实说明）

Android 的后台限制是**系统级**的，App 无法完全对抗：

1. **Doze（打盹）**：熄屏静止一段时间后进入 Doze，网络访问被挂起，只在维护窗口放行；我们无法用普通唤醒锁绕过。表现：**深睡时开播提醒可能延迟**（数分钟到下一次维护窗口）。
2. **App Standby / 后台限制**：长时间未使用会被降级，网络与唤醒被限制。
3. **厂商电池管理**：华为/荣耀/小米/OPPO/vivo/三星等对后台进程有额外“自启动/关联启动/深度睡眠/智能省电”策略，可能直接杀掉前台服务或推迟网络。
4. **Android 12+ 后台启动前台服务限制**：App 在后台时不能随意启动 FGS；本 App 服务启动失败时会安全退出，需要用户重新打开 App。
5. **没有开机自启**：手机重启后需打开一次 App 才会恢复监测（刻意设计，减少后台启动面）。

**用户指引（应用内设置页已提供入口）**：

- 设置 → 电池 → 找到「直播监测」→ 选择“不限制/允许后台活动”（不同厂商路径不同）。
- 设置页提供“电池优化状态”检查与跳转**系统电池优化列表**的按钮（`Settings.ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS`）。
  - 注意：本 App **不申请** `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 权限，也不会弹系统级“忽略电池优化”直接授权框；由用户自行在系统设置中决定，避免滥用白名单与商店政策风险。
- 部分厂商需额外在“最近任务”中锁定本 App，或关闭“深度睡眠/智能省电”。

**不建议**：为了提醒及时性长期把 App 加入电池优化白名单（会更耗电，也可能被商店视为滥用后台）；优先调大检测间隔、减少房间数。

## 8. 与桌面版行为差异小结

| 维度 | 桌面版 | Android |
| --- | --- | --- |
| 后台载体 | 托盘进程 | 前台服务 + 常驻通知 |
| 唤醒机制 | 事件等待，零 CPU | 协程挂起 + 每房间短唤醒锁 |
| 间隔 | 默认 30s | 默认 60s（最短 15s） |
| 请求节奏 | 固定 120ms | 120ms + 0–2s 抖动 |
| 深睡影响 | 无（PC 不休眠/睡眠策略不同） | Doze 会推迟网络，提醒可能延迟 |
| 重启恢复 | 开机自启 | 无开机自启，需打开 App 一次；`START_STICKY` 尽力恢复 |
| 提醒形态 | 置顶弹窗 | 高优先级通知（锁屏内容 PRIVATE） |

## 10. 已知限制

- 无真机（LDPlayer 模拟器已完成 v1.0.0 与 v1.1.0 核心链路动态验证；未覆盖真机 ARM/厂商 ROM、Doze/厂商杀后台、24h 长跑、抓包、提示音可闻性与后台 BAL 自动打开，见 `安全测试报告.md` 第 8.6 节）。
- TLS 证书固定为 **CA 家族级**：平台换 CA 会检测失败（可用设置开关临时关闭）；pin 需随平台证书变化维护；固定不隐藏客户端 IP。
- **自动打开直播间受 Android 10+ 后台 Activity 启动（BAL）限制**：可能被系统静默拦截，日志可能显示已执行但实际未打开（SEC-103）；默认关闭。
- **外部跳转残余风险（v1.1.1）**：平台 App 跳转显式 `setPackage`；浏览器先 `resolveActivity` 再 `setPackage`（解析失败回退隐式，低风险）；**已下架下载 App/应用市场/官网跳转**，攻击面减少。
- **通知渠道迁移**：旧 `live_alerts` 渠道会被删除，用户旧渠道自定义声音设置丢失；提醒音改由 App 播放器播放（SEC-104）。
- **自定义提示音**：依赖系统 MediaPlayer 解码用户音频，损坏/不支持时回退内置音；2MB 上限、内部私有目录、不申请存储权限。
- 平台页面结构随时变化：解析失败会退化为“检测失败（橙色）”而不是误报。
- 抖音/虎牙等平台偶发反爬/限流：表现为“接口受限/限流，稍后自动恢复”，不做绕过。
- `START_STICKY` 在“用户强制停止/系统限制后台启动”时不会恢复，需要用户手动打开 App。
- 长时间深睡时提醒可能延迟；这是 Android 平台限制，不是 App 缺陷，需在应用商店说明与用户指引中如实告知。
